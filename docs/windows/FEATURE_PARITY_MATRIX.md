# Feature Parity Matrix — Mira macOS → Windows

Every row is backed by evidence in [REPOSITORY_EVIDENCE.md](REPOSITORY_EVIDENCE.md) — follow the file/symbol column back there for the full citation. **Confidence** reflects how solidly this audit confirmed the *macOS* behavior from source (not whether the Windows work is easy). **Rewrite scope** is this audit's judgment about how much of the Windows implementation can reuse existing logic vs. needs new design.

## Reading this matrix

- **Reuse backend fully** rows (23, 26–29) are the highest-leverage, lowest-risk Windows work — they require no changes to the Supabase/Node backend at all, only a new HTTP/WebSocket client. This is why [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) recommends starting there.
- **Full rewrite** rows (1, 2, 5, 34, 35) are UI-shell or platform-integration features with no macOS code to reuse conceptually beyond the underlying business rules — budget these as net-new Windows engineering, not porting.
- Rows marked **Unknown / conditional** (10, 24, 30) need a follow-up investigation — specifically, whether Anthropic/OpenAI ship Windows builds of the `codex`/`claude` CLIs — before they can be scoped at all. Do not assume parity on these until verified.
- Several macOS features (AirDrop share, custom-Dock OS toggles, AppleScript-only skills) have **no Windows equivalent as a matter of platform architecture**, not just an implementation gap — these should be explicit, named exclusions in scope discussions, not silently dropped.
