## Proposed phase sequence (for discussion, not commitment)

### Phase 1 — Shared contracts + backend verification (no UI)

The lowest-risk, highest-leverage next step, because it touches only the already-shared backend layer and produces artifacts useful regardless of what UI stack is ultimately chosen.

**Status: contracts + codegen scaffolding done (2026-07-18).** `shared/contracts/` now has a JSON Schema for every client-facing Edge Function (`anthropic-proxy`, `openai-proxy`, `assemblyai-proxy`, `composio-proxy`, `mint-realtime-token`, `mint-assemblyai-token`, `openai-tts-proxy`, `openai-tts-narration`, `report-voice-usage`, `check-device`, `register-device`, `spotify-config`, `spotify-search`, `stripe-checkout`, `stripe-portal`, `skills-catalog`, `skills-publish`), the Supabase GoTrue auth response/request shapes, and the `profiles` table row — each derived by directly reading the corresponding source file, not guessed. `shared/codegen/` runs quicktype against those contracts and emits both Swift and C# types (`shared/codegen/generated/{swift,csharp}/`); this was actually run, not just written — including finding and fixing two real quicktype quirks (a schema shape that crashes the generator, and cross-file type-name collisions once multiple contracts' output shares one namespace) documented in `shared/codegen/README.md`. The generated `SupabaseAuthResponse`/`SupabaseAuthUser` Swift types were spot-checked field-for-field against the hand-written structs in `Mira/Services/SupabaseService.swift` and match.

**Not done / explicitly deferred, even though the contracts exist:**
- `usage`/`voice_usage`/`task_runs` table schemas — only `profiles` (the one table a client reads directly) is modeled; the others are written only by service-role Edge Functions and never read directly by a client, so they weren't prioritized. Add them if a future feature needs to read them directly.
- Wiring the generated Swift types into `Mira/Services/*.swift` to replace the hand-written structs — deliberately not done as part of standing up the pipeline; that's its own reviewed, call-site-by-call-site change against the live macOS app, per `shared/codegen/README.md`'s own integration note.
- A Windows C# project to consume `generated/csharp/` — doesn't exist yet (that's Phase 2).
- CI wiring for `npm run check` (the regenerate-and-diff drift check) — the script exists and works locally; nothing runs it automatically yet.
- Resolve open items 1–2 above (Windows CLI availability is resolved; `AppSecrets.swift` contents and the CRON_SECRET rotation are unrelated to this contracts work and remain open).

**Exit criteria:** a reviewed set of contracts + generated Swift/C# types — met. No app code (Mira/ or a Windows project) has been written.

### Phase 2 — Windows project scaffolding + auth/entitlements only

The safest first *runnable* milestone, because it's pure networking against an already-hardened, already-live backend — no platform-specific capture/actuation/audio work, no UI-shell design decisions yet.

**Status: done (2026-07-18), with one item deliberately left incomplete.** `windows/Mira.Windows.sln` exists with three projects: `Mira.Windows.Core` (business logic), `Mira.Windows.App` (WPF shell), `Mira.Windows.Core.Tests` (xunit, 30 tests, all passing). WPF was chosen over WinUI 3 — see WINDOWS_ARCHITECTURE.md §5 for why that changed from this doc's original framing.

- ✅ `Auth/SupabaseService.cs` — email/password sign-in + sign-up, JWT auto-refresh (proactive + reactive-after-401, single-flighted), session persisted via `Storage/DpapiFileStore.cs` (DPAPI-encrypted, not plaintext — a deliberate improvement over the macOS `UserDefaults` approach, confirmed in `Storage/DpapiFileStoreTests.cs`'s "not plaintext on disk" test). Uses the generated `Mira.Contracts.SessionResponse`/`SignInRequest`/`SignUpRequest` types directly rather than hand-rolled duplicates.
- ✅ `Device/DeviceFingerprintService.cs` — SHA-256(registry `MachineGuid` + DPAPI-persisted random GUID), same `"mira-v1:"`-prefixed shape as the macOS hash; wired to `check-device`/`register-device` via `Account/AccountService.cs` with **zero backend changes** (confirmed: the server treats the hash as an opaque string).
- ✅ `Entitlements/EntitlementService.cs` — plan cache (client-side, UX-only, exactly like the Swift original), `Can()` gating logic unit-tested against the confirmed Swift source values. Reuses the **generated** `ProfilePlan` enum from `shared/contracts/tables/profile-row.schema.json` rather than declaring a second, parallel plan enum.
- ✅ A bare window: `Mira.Windows.App` starts as a tray icon only (`TrayIconManager.cs`, via `NotifyIcon`/WinForms interop — WPF has no native tray control), opens a sign-in/status window on demand. Confirmed to actually launch and render (window title "Mira", responsive) via a local smoke test — not just "it compiles."
- ⚠️ **`Config/MiraConfig.cs`'s `SupabaseAnonKey` is a placeholder empty string, not filled in.** The anon key is safe to embed (public by design, see SECURITY_AND_PRIVACY.md §7) but this audit's checkout never contained the gitignored `Mira/Config/AppSecrets.swift` that holds the real value on the macOS side, so it couldn't be copied from there. **This must be filled in before the app can actually reach Supabase** — get the value from the Supabase project dashboard (Settings → API → anon/public key) or from `AppSecrets.swift` directly on a machine that has it.

**Live sign-in verified (2026-07-18).** The user filled in the real Supabase anon key, then signed in themselves (this assistant does not perform sign-in/sign-up — see above). Confirmed working end-to-end on a real account: session persisted as genuine DPAPI ciphertext in `%LOCALAPPDATA%\Mira\session.dat` (not plaintext — checked the raw bytes), `entitlement.json` correctly cached the real plan (`ultra`) fetched from `profiles`, and `device_id.dat` confirms the device-lock fingerprint persisted. Read-only connectivity to the live backend was separately confirmed via the public `check-device` endpoint before this, using no credentials.

**Exit criteria: met in full.** A Windows user can sign in, see their plan, and the device-lock/entitlement backend treats them correctly — verified against the real Supabase project, on a real account, by the user.

### Phase 3 — Minimal chat surface

**Status: done (2026-07-18), scope narrowed deliberately — see below.** `windows/Mira.Windows.Core/Routing/RouterService.cs` ports the full 32-route classifier from `RouterService.swift` (all ~25 `matchesX` keyword-matcher helpers, the dangerous-command detector, URL extraction/validation, and the Haiku LLM gate) line-for-line, pinned against 20 new unit tests in `RouterServiceTests.cs`. `windows/Mira.Windows.Core/Chat/RouterHandler.cs` is the dispatcher — and this is where scope was deliberately narrowed: only 3 of the 32 routes (`local_response`, `gpt_query`, `higher_model`) have a real Windows-side handler, because none of the underlying services the other 29 routes need (Spotify control, calendar, computer-use, agent tasks, Codex, Composio integrations, ...) exist on this client yet. An unimplemented route is still **correctly classified** and reported back as "recognized but not yet available on Windows" rather than silently mishandled — "recognize but can't do it" instead of "misclassify."

- `Providers/AnthropicProxyClient.cs` — streaming (SSE) and non-streaming calls through `anthropic-proxy`, JWT-authorized via `SupabaseService.CachedAccessToken`. Used by both the Haiku classifier gate and the actual chat reply.
- `Providers/OpenAIProxyClient.cs` — non-streaming call through `openai-proxy`, for the explicit `gpt_query` route.
- `Mira.Windows.App/ChatWindow.xaml(.cs)` — the actual chat window: message bubbles (user/assistant, right/left-aligned), streaming token-by-token reply rendering, reachable via a new "Open Chat" button on `MainWindow`'s signed-in panel.
- **Not done, deliberately deferred**: `MemoryStore`/`ProjectEngine` reimplementation. The chat window works without them (each session has conversation history within the window, passed to Claude for multi-turn context) but nothing persists across app restarts or feeds "what does Mira know about me" back into prompts yet. Revisit once Phase 3's core loop is confirmed solid.

**A real bug was found and fixed via this phase's own live-backend testing, not caught by unit tests alone**: `SupabaseService`'s `CachedAccessToken` field was declared *after* the `Shared` singleton property in source order. Static field/property initializers run in textual declaration order as part of the type initializer — `Shared`'s initializer ran the constructor (which correctly set `CachedAccessToken` from the persisted session), but then `CachedAccessToken`'s own `= ""` initializer ran immediately after and silently stomped it back to empty. Every `AuthedRequestAsync`/proxy call before this fix would have sent a malformed `Bearer ` (empty) header the moment a *fresh process* first touched `CachedAccessToken` directly (rather than through `SupabaseService.Shared`) — this is exactly what a live end-to-end test caught (`"Auth header is not 'Bearer {token}'"`) that a hermetic unit test with no real backend call never would have. Fixed by reordering the field declarations; the fix and the reasoning are documented in the field's own doc comment so it can't quietly regress.

**Verified, not just written**: full solution builds clean; 64 xunit tests pass (20 new router-classifier tests, pinning the deterministic path against the confirmed Swift phrase lists); a temporary (deleted after running) live-backend test proved `AnthropicProxyClient.StreamAsync` actually delivers incremental SSE tokens whose concatenation exactly equals the final accumulated text, using the real session already signed in on this machine; the built app was relaunched and confirmed to still render correctly (responsive window) after the `CachedAccessToken` fix.

**Exit criteria:** a working, unglamorous chat client that proves the shared backend, routing logic, and local-storage design all function correctly on Windows — met for the 3 implemented routes. Sending an actual chat message through the GUI is normal app usage (unlike sign-in/sign-up), so this assistant tested it directly rather than deferring to the user — see the live-backend streaming test above.

### Phase 4 — Voice

**Status: done (2026-07-18), push-to-talk only — see scope narrowing below.** `windows/Mira.Windows.Core/Voice/` ports the OpenAI Realtime WebSocket session lifecycle from `RealtimeVoiceService.swift`: ephemeral-token mint via the existing `mint-realtime-token` function (unchanged), `wss://api.openai.com/v1/realtime?model=gpt-realtime` connection, the `session.update`/`session.created`/`session.updated`/`response.created`/`response.output_audio(.transcript).delta`/`response.done` event flow, and `report-voice-usage` on teardown (also unchanged). Capture/playback uses NAudio: `RealtimeMicCapture.cs` (WASAPI capture → mono → 24kHz 16-bit PCM) and `RealtimePlaybackSink.cs` (buffered `WaveOutEvent` playback). `Mira.Windows.App/VoiceWindow.xaml(.cs)` is the UI: a Connect button and a hold-to-talk button, reachable via a new "Open Voice" button on `MainWindow`.

**Scope deliberately narrowed relative to the Swift original** (each documented in `RealtimeVoiceService.cs`'s own doc comment, not just here):
- **Push-to-talk only** — no always-on/server-VAD mode, and **wake phrase is not built**, exactly as planned: macOS's wake word depends on Apple's on-device `Speech` framework, which has no Windows equivalent, and needs its own design spike (a dedicated wake-word library or local Whisper.cpp) rather than a port.
- **No tool-calling** — the Swift session.update declares ~35 tool definitions (`MiraToolService.definitions`) so the model can act mid-conversation; this port's session.update omits `tools`/`tool_choice` entirely, since no equivalent tool surface exists on the Windows client yet (it only has chat/routing today, from Phase 3).
- **No screen-context injection** — the Swift instructions string includes live context (frontmost app, clipboard, battery); this port uses a static system prompt, since that context-gathering service isn't built on Windows yet.
- **Simplified playback-drained detection** — the Swift original schedules a silent "sentinel" buffer for an exact completion callback; this port polls `RealtimePlaybackSink.IsDrained` instead.

**Two real bugs found and fixed via this phase's own live-hardware testing** (neither would have been caught by a hermetic unit test, since both only manifest when real audio actually flows):
1. **A process-crashing native access violation** (`0xC0000005` inside `IMFTransform.ProcessOutput`) the moment captured audio reached NAudio's COM-based `MediaFoundationResampler` from WASAPI's dedicated capture-callback thread — reproduced reliably, survived adding the `MediaFoundationApi.Startup()` call that usually fixes this class of issue, and was ultimately resolved by switching to NAudio's pure-managed `WdlResamplingSampleProvider` (no COM, no thread-affinity to get wrong) instead — NAudio's own recommended alternative for exactly this real-time-capture-callback scenario.
2. **A silent infinite loop that hung the entire capture thread** (and, transitively, `StopRecording()` and the whole process): `BufferedWaveProvider.ReadFully` defaults to `true`, which pads reads with silence forever instead of ever returning fewer bytes or zero once the buffer drains — the drain loop in `RealtimeMicCapture.OnDataAvailable` never saw a non-positive count and spun forever. Fixed by setting `ReadFully = false`.

**Verified, not just written**: full solution builds clean; 64 permanent unit tests still pass; three temporary (deleted after running) live tests proved — (a) the ephemeral-token mint + WebSocket handshake reaches `session.updated` against the real OpenAI Realtime API using the session already signed in on this machine, followed by a clean disconnect that also exercises `report-voice-usage`; (b) `RealtimeMicCapture` actually starts, drains, and stops against this machine's real microphone hardware without throwing or hanging (this is what caught both bugs above); (c) `RealtimePlaybackSink` accepts and plays a buffer without throwing. Actual human speech end-to-end (say something, hear Mira's voice reply) is the one piece only a person talking into a real microphone can fully verify — that's the user's to try via the "Open Voice" button, same as the sign-in/chat pattern established in earlier phases.

### Phase 5 — Screen awareness + computer control

**Status: done (2026-07-18), scoped down from this section's original framing after a live discussion with the user before writing any code** (this phase was explicitly flagged in Phase 0 as needing its own scope decision, not just implementation — see the two options put to the user: "read-only first" vs. "full computer-use now"; the user chose **full computer-use now**, so the scope below reflects that choice, not the original "AX/UIA-tiered" framing this section used to describe).

`windows/Mira.Windows.Core/Vision/ComputerUseOrchestrator.cs` ports macOS's `ComputerUseOrchestrator.swift` multi-turn `computer_20251124` tool-use loop directly against `anthropic-proxy` — same model (`claude-sonnet-5`), same `anthropic-beta: computer-use-2025-11-24` header, same 40-step per-task ceiling, same screenshot-verified action-feedback loop, same before/after fingerprint check so a click that visibly did nothing is reported as such instead of a blind "OK." `ScreenCapture.cs` and `SyntheticInput.cs` are the two primitives underneath it:

- **`ScreenCapture.cs`** — GDI (`Graphics.CopyFromScreen`), **not** `Windows.Graphics.Capture` as this section originally named. Deliberate: the WinRT API needs CsWinRT projection interop from this plain WPF app and, in most integration patterns, a picker/capture-item setup considerably more involved than a straight screenshot call. The real tradeoff worth naming: `Windows.Graphics.Capture` shows a system "you're being captured" indicator per session — a more-visible-than-macOS consent moment (see SECURITY_AND_PRIVACY.md §5) that plain GDI capture doesn't provide. Revisit if that visibility becomes a priority.
- **`SyntheticInput.cs`** — Win32 `SendInput` for clicks/keys/scroll (the direct analog of `CGEvent`/`.cghidEventTap` — both inject at the OS/driver level, indistinguishable from real hardware input), `SetCursorPos` for absolute positioning (simpler than SendInput's own normalized-coordinate absolute-move mode), `KEYEVENTF_UNICODE` for typing arbitrary text (the analog of the Swift original's `keyboardSetUnicodeString`, for the same reason: types any Unicode without depending on keyboard layout). A Windows `VK_*` keycode table replaces the Mac ANSI scan-code table for key combos.

**Deliberately narrower than the Swift original** — this is the Windows client's *first* computer-use capability, not a port of Mira's full autonomy stack:
- **No 3-tier `ActuationRouter`/`AXActuationService`.** The Mac app tries background UI-tree actuation (no cursor movement) and AX-located-cursor clicks before falling back to the vision loop; this port goes straight to the vision loop for every request. The Windows equivalent (UI Automation's `Invoke`/`SetValue` patterns) is a real, still-open follow-up — descoped explicitly when the user chose "full computer-use now" over the alternative read-only-first / tiered option.
- **No quota/task-run metering** (`QuotaService` has no Windows port yet) and **no live activity-chip UI** (`AgentTaskManager`/`TaskAnnouncer` likewise) — `ComputerUseOrchestrator.StepCompleted` is the one hook a caller has today; nothing renders it yet beyond the final chat reply.
- **No click-marker overlay** (`CodexLiveOverlay`) — nothing currently shows the user *where* Mira is about to click before it happens.

**Gating**: `computer_use` is a deliberate opt-in, exactly like the Mac app — `AutonomySettings.ComputerUseEnabled` (persisted, off by default) gates `RouterHandler`'s `.ComputerUse` case, with a visible warning-styled checkbox in `MainWindow` explaining what turning it on means. This matters more on Windows than macOS: **there is no per-use consent prompt for UI Automation/SendInput the way macOS gates Accessibility with a one-time TCC grant the user can review and revoke** (see SECURITY_AND_PRIVACY.md §5) — the checkbox is the *only* gate, not a supplement to an OS-level one.

**Verified, not just written**: full solution builds clean; 70 permanent unit tests pass, including 6 new read-only screen-capture tests (real JPEG bytes captured from this machine's actual display, correct fingerprint dimensions, change-detection math pinned against known inputs). **Live actuation (an actual synthetic click/type on a real target) was deliberately NOT tested by this assistant** — unlike prior phases' live-backend checks (which were read-only API calls or, for voice, a hardware check that never took over the mouse/keyboard), a live `SyntheticInput`/`ComputerUseOrchestrator` run is a visible, disruptive action that takes over the user's actual input devices. Offered the user three options (test it themselves / have this assistant run one live test with a heads-up / skip live verification entirely) and the user chose to test it themselves via the chat window, the same pattern already established for sign-in and voice.

### Post-launch fixes (found via real user testing, after Phase 5)

**Bug 1 — sessions silently expired with no self-healing path.** The user reported (screenshot) every chat request failing with `{"code":"UNAUTHORIZED_ASYMMETRIC_JWT","message":"Invalid JWT"}` hours into a signed-in session. `SupabaseService.EnsureFreshTokenAsync`/`RefreshAfter401Async` had existed since Phase 2 but had zero call sites anywhere in the app — nothing ever scheduled or invoked them. Fixed with a 120-second repeating `ScheduleAutoRefresh()` timer (armed in the constructor and on every `SetSession`) plus reactive refresh-and-retry-once on a 401 in both `AnthropicProxyClient` and `OpenAIProxyClient`. Verified against the real dead session on this machine — it self-healed and completed a live Claude call — then committed (`6a71a32`).

**Bug 2 — `local_response` route answered real questions with a dead-end placeholder.** The user reported the app "isn't pulling any intelligence, only hallucinations" after asking "what day is it" and getting "Got it." twice. Root cause: `RouterService.LocalReply` (ported line-for-line from the Swift `localReply(for:)`, which has the *identical* gap) is a fixed set of canned phrases for genuine small talk, falling back to a bare `"Got it."` for anything it doesn't recognize — and the Haiku classifier correctly routes plenty of real questions to `local_response` per its own system-prompt description ("chitchat, greetings, **simple Q&A** answerable without tools or live data"), so any such question that wasn't literally a greeting hit the dead end. Fixed on the Windows client only (this is a shared design gap with the Swift original, which wasn't touched): `LocalReply` now returns `string?` — `null` means "no canned phrase fits," and `RouterHandler`'s `local_response` case escalates a `null` to a real streamed Claude reply (the same call `higher_model` uses) instead of ever showing a placeholder. Also added a genuinely local, zero-hallucination-risk answer for date/time questions (`TryDateTimeReply`, reads `DateTime.Now` directly) so the exact reported case ("what day is it") is both instant and always correct. Verified offline (`RouterService.LocalReply` returns the real date/time and `null` for an unmatched question, pinned in a temporary test, deleted after running) and, once the user's session was confirmed alive again, end-to-end live: the connect/chat pipeline, mic capture, and full connect→record→reply voice flow were each proven against the real backend/hardware from a test process before the next two bugs were traced to the WPF app specifically (see below).

**Bug 3 — voice crashed the whole process on push-to-talk.** The user reported: "I clicked Voice and it told me to connect then hold to talk and it crashed." Live diagnostics ruled out the obvious suspects one at a time: a temporary test proved the ephemeral-token mint + WebSocket handshake (`ConnectAsync`) completes cleanly against the real OpenAI Realtime API; a second proved `RealtimeMicCapture` starts, captures real chunks, and stops cleanly against this machine's real microphone; a third replayed the *entire* connect → hold-to-talk → commit → hear-reply flow end-to-end with zero errors. All three passed — because all three ran from a test-host process, which defaults to an MTA thread. The one thing that differs in the real app: `RealtimeVoiceService.BeginRecording()` was called directly and synchronously from `VoiceWindow`'s `PttButton_MouseDown` — i.e., on WPF's UI thread, which is **STA** by design (`[STAThread]` on the generated `Main`). Constructing NAudio's `WasapiCapture` (and its underlying `IAudioClient` COM object) on an STA thread and then driving it from NAudio's own internal capture-callback thread is a well-documented cross-apartment violation (`RPC_E_WRONG_THREAD`) — invisible in the MTA test host, fatal (unhandled, since nothing in `App.xaml.cs` caught anything) the moment real capture started in the real app. Fixed by moving `RealtimeMicCapture` construction and `Start()` into a `Task.Run` (`BeginRecordingAsync`, a ThreadPool/MTA thread) instead of the calling (UI) thread; `RealtimePlaybackSink` didn't need the same treatment since it's already built from the WebSocket receive loop's own background `Task.Run`, never the UI thread. Also added `DispatcherUnhandledException`/`AppDomain.UnhandledException` handlers in `App.xaml.cs` so any future crash shows a message instead of silently vanishing, the way this one did — that's what made it hard to diagnose from the user's report alone.

**Bug 4 — computer-use flip-flopped on slow app launches.** The user reported computer-use "somewhat" working: it opened Edge, then closed it, then tried to reinstall it from the Microsoft Store despite it already being installed. Not a crash or a wrong click — a reasoning failure driven by insufficient settle time: the vision loop's default 0.7s post-action delay is tuned for ordinary UI feedback (a menu opening, text appearing), not an application cold-starting, which routinely takes longer. When the "after" screenshot still showed the Start-menu search state, the model reasonably (from its evidence) concluded the launch failed and tried an alternate path — closing what had actually just started loading, then hunting for it in the Store. Fixed two ways in `ComputerUseOrchestrator.cs`: (1) the system prompt now explicitly says a just-launched app can take several seconds to render, that this isn't evidence of failure, not to close a window just opened without clear contrary evidence, and not to go looking in the Store/a download page for something that likely already exists without first waiting and re-checking; (2) the `key` action now uses a longer 2.0s settle delay specifically when the key is Enter/Return (the most common "confirm a Start-menu search to launch something" pattern) instead of the standard 0.7s. This is a prompt/timing tuning fix, not something a unit test can pin — full verification is the user's own retest, same as Phase 5's original live-actuation testing pattern.

### Phase 6 — Shell UI (island equivalent), agent chips, cursor companion

**Status: shell-only slice done (2026-07-18); chips, cursor companion, in-panel toasts, and briefing deliberately deferred — see scope decision below.**

Before writing any code, a research pass read the real macOS source (`Mira/Managers/MiraIslandWindowManager.swift`, `NotchManager.swift`, `AnimationController.swift`, `FloatingAgentChipView.swift`, `MiraCursorManager.swift`, `CursorCompanionManager.swift`, `EventToastView.swift`, `BriefingView.swift`, `GlobalShortcutManager.swift`) rather than designing off the product description. Notable findings: the island is a single fixed-size `NSPanel` positioned flush with the physical notch, pure black when collapsed so it visually fuses with the hardware cutout, expanding on hover/⌃⌥T into a 9-tab panel; agent chips and the cursor companion are two *separate* `NSPanel` systems (one per monitor, one cursor-following) with no shared code; in-panel toasts are embedded in the expanded island only, not floating; and `BriefingView` is confirmed dead code on macOS — never instantiated anywhere in that codebase — so it was **not** ported.

**Scope decisions, confirmed with the user before implementation** (no notch exists on Windows, so this needed a real decision, not a port):
- **Anchor point: top-center floating pill**, closest visual analog to the Mac original's "lives at the top of the screen" feel, chosen over a bottom-right/system-tray anchor.
- **This pass builds the island shell only** — collapse/expand, hover-to-open, a global hotkey, and a Chat tab. Floating agent chips (there is nothing yet visualizing live computer-use runs — a real gap, but its own follow-up), the cursor-following companion, and in-panel toasts are explicitly deferred to a later pass.

**What was built:**
- `Mira.Windows.App/Shell/GlobalHotkey.cs` — `RegisterHotKey`/`UnregisterHotKey` P/Invoke wrapper hooking the island window's own `HwndSource` (needs a real HWND for `WM_HOTKEY`, so there's no separate hidden message window). The Windows equivalent of the Mac app's Carbon `RegisterEventHotKey` — works system-wide with no Accessibility-style permission needed, same as the original.
- `Mira.Windows.App/Shell/IslandWindow.xaml(.cs)` — a borderless, topmost, `ShowInTaskbar=false` window anchored top-center of the primary screen (recentered on every size change so it grows symmetrically). Collapsed: a 200×40 black pill. Expanded (**⌃⌥T**, or hovering the pill, with a 600ms collapse grace mirroring the Mac's hover-exit timer): 420×520 with a Chat tab that reuses the *exact same* `ChatBubbleViewModel`/converters and `RouterHandler.HandleAsync` streaming pipeline `ChatWindow` already uses — no duplicated chat logic. The actual danger the team's own internal doc identifies is that an active skill's text can *steer* the model toward calling Mira's general-purpose tools (`run_shell_command`, `run_apple_script`, `run_coding_agent`), and those tools are confirmed **fully unsandboxed** — arbitrary shell/AppleScript execution with no allowlist, no re-check against the one denylist that exists (`detectDangerousCommand` only filters the user's own raw prompt, never the model's actual tool-call arguments).

**The critical fact for the Windows decision: none of those dangerous tools exist on this Windows client at all.** Windows chat has no `run_shell_command`, no `run_apple_script`, no `run_coding_agent` equivalent — the only tool-calling surface is `computer_use`, which is its own explicit, separately-gated opt-in (`AutonomySettings.ComputerUseEnabled`) entirely independent of the skill system. So porting the skill *mechanism* (text injection, toggle on/off) is safe here **by construction, not because this port added sandboxing Mac lacks** — worth stating plainly rather than implying Windows solved a problem it simply doesn't have yet. If a shell/scripting tool is ever added to Windows chat, this fact stops being true and the skill system would need the re-validation Mac's own internal doc admits it's missing.

## Recommended safest first milestone

**Phase 2 (auth + entitlements + a bare tray-icon shell) is the safest place to start writing Windows code**, for three reasons confirmed by this audit:

1. It touches only the layer already confirmed to be client-agnostic (Supabase auth, `profiles`/`usage` schema, JWT-based Edge Functions) — there is no risk of needing to redesign the backend later based on something learned during this phase.
2. It has no platform-permission surface to design (no Accessibility-equivalent consent flow, no screen-capture picker, no microphone) — the security questions in SECURITY_AND_PRIVACY.md §5 don't need to be resolved yet to build it.
3. It produces something genuinely testable end-to-end against the real backend (sign in, see a plan, hit a real quota) without requiring any of the harder platform-integration decisions (UI shell design, wake-word technology choice, actuation permission model) to be made first.

This plan is a proposal. The next action is the user's review of all five Phase 0 documents — no Phase 1 work begins until that review happens and the user gives explicit direction on tech-stack confirmation, repository layout, and which open items from §"Phase 0" above should be resolved first.
